## 2. 当前起点与第一版范围

### 2.1 已确认的起点

- 当前目录名称虽然叫 `Uni-app`，工程实际上是原生 HarmonyOS 工程，采用 ArkTS / ArkUI，并非 DCloud uni-app 工程。
- `entry/src/main/ets/pages/Index.ets` 仍是 Hello World 页面。
- `entry/src/main/module.json5` 当前没有声明网络权限。
- `build-profile.json5` 当前配置的兼容和目标 SDK 均为 `26.0.0`，签名配置数组为空；应在本机 DevEco Studio 核实 SDK、设备支持和签名，不要直接照抄网上另一版本的配置。
- 后端采用 Spring Boot，网页端采用 Next.js。鸿蒙 App 直接连接后端，无需经过网页代理。
- 接口文档标注的后端基线为 `feature/web-v2`、提交 `f5ca396`。开始联调前应确认实际运行版本；此处不代表已经核验当前检出的提交。

### 2.2 第一版做到什么程度

完成：游客浏览 → 注册登录 → 商品和规格选择 → 购物车 → 地址 → 跨店提交订单 → 查询与取消订单 → 售后申请与记录。限时抢购作为主流程稳定后的扩展。

当前能做的是开发演示版交易流程，尚不是可正式收款、发货的生产商城。

| 能力 | 当前依据 | 第一版安排 |
|---|---|---|
| 店铺、搜索、商品、SKU | 已有接口 | 接入真实数据 |
| 登录、购物车、地址、结算、订单 | 已有接口 | 主线优先完成 |
| 售后、限量促销 | 已有接口 | 后续阶段接入 |
| 商品图片 | 当前没有正式字段和上传接口 | 统一占位图，等待图片合同 |
| 分类树、首页运营配置 | 当前没有对应正式接口 | 采用店铺浏览和搜索，不虚构分类数据 |
| 支付 | 只有模拟支付接口 | 用户版本不提供模拟付款 |
| 发货、物流、确认收货、真实退款 | 当前缺失 | 等后端补齐后实现 |
| 收藏、评价、优惠券、消息、验证码登录 | 当前缺失 | 第一版不放可点击的假入口 |
| 商家运营、AI 经营功能 | 不属于消费者主流程 | 第一版不接入 |

## 3. 页面布局与导航安排

底部先采用四个入口：**首页、逛店、购物车、我的**。当前没有分类树接口，因此第二栏先叫“逛店”。将来后端支持商品分类后，再评估是否改成“分类”。

| 页面 | 从上到下的布局 | 主要去向 |
|---|---|---|
| 首页 | 搜索入口、分层快捷入口、活动区域、商品列表 | 搜索、活动详情、店铺、商品 |
| 逛店 | 店铺列表、店铺名称与商品数 | 店铺商品列表 |
| 搜索 | 搜索框、店铺筛选、结果列表、加载更多 | 商品详情 |
| 店铺 | 店名、商品列表 | 商品详情 |
| 商品详情 | 占位图、名称、价格、描述、规格、库存、底部购买操作 | SKU 弹层、购物车 |
| 购物车 | 按店铺分组的商品、失效商品提示、底部勾选与结算栏 | 确认订单 |
| 我的 | 登录信息、订单、地址、售后、设置 | 账户相关页面 |
| 确认订单 | 收货地址、按店铺分组的商品、金额说明、提交按钮 | 结算结果 |
| 订单详情 | 状态、订单号、商品、金额、地址快照、允许执行的操作 | 取消、售后 |

商品展示先用简单双列卡片；购物车和订单使用单列信息卡片。先把字号、留白、按钮和状态统一，再增加玻璃、悬浮、渐变等效果。

### 3.1 首页快捷入口：主功能卡 + 轻量入口

首页不采用等宽、密集、纯白底的传统九宫格。快捷区采用“主功能卡 + 轻量入口”的两层布局，保留快捷入口的易用性，也让首页更像有品牌感的商城。

```text
搜索商品、店铺

┌────────────────┐  ┌────────────────┐
│ 🔥 限时抢购      │  │ 🏬 精选店铺      │
│ 今日好价         │  │ 去逛一逛         │
└────────────────┘  └────────────────┘

🛍 热门商品   🛒 购物车   📦 我的订单
📍 收货地址   ♻ 售后服务  ⋯ 全部服务
```

两张主功能卡使用较大的留白和短文案：限时抢购可使用暖橙红色，精选店铺可使用项目品牌主色或深墨绿色。下方六个入口使用统一线性图标和简短标题，不做彩色图标堆砌；购物车和订单允许显示数量角标。

首批入口只跳转到已有能力：限时抢购、精选店铺、热门商品/搜索、购物车、我的订单、收货地址、售后服务。“全部服务”仅展示已实现或已明确设计的入口；收藏、优惠券、物流、评价等接口尚未存在时，不放置可点击的假功能。

视觉原则：页面背景使用暖白或浅灰，主卡使用 20～24vp 圆角，图标风格统一，卡片利用大小与色彩形成层次。后续可以根据 Pixso 设计稿调整样式，但不改变入口标识和跳转逻辑。

初期商品页只做“加入购物车”和“去购物车”。“立即购买”需要单独确认语义：当前结算使用购物车项 ID，没有独立直接购买接口，不要用偷偷增删购物车的方式冒充该能力。

“我的订单”先按后端实际状态展示：待付款、已付款、已取消、已关闭。暂不显示没有后端支持的“待发货”“待收货”。

## 4. 代码组织：以后换组件时不重写业务

页面负责组合，展示组件负责呈现，业务状态负责协调操作，API 层负责接口调用。

```text
entry/src/main/ets/
├─ entryability/             保留现有应用入口
├─ pages/                    页面和主页面容器
├─ components/
│  ├─ common/                按钮、加载、错误、空状态
│  ├─ navigation/            底部 AppTabBar
│  ├─ product/               商品卡片、SKU 选择器
│  └─ order/                 订单卡片、状态标签
├─ viewmodel/                页面业务状态与操作
├─ repository/               页面使用的数据入口，隔离真实与 Mock 数据
├─ api/                      AuthApi、CartApi 等接口封装
├─ network/                  HttpClient、ApiError
├─ model/                    请求、响应和界面数据类型
├─ session/                  会话保存、恢复、退出
├─ navigation/               页面参数、导航处理
├─ theme/                    颜色、间距、圆角、字号
└─ config/                   环境配置
```

按实际进度创建文件，不用一次搭完所有空类。先完成一个商品列表的数据通路，再复用结构。

### 4.1 底部 Bar 的替换约定

固定它的输入：导航项、当前选中项、购物车角标；固定它的输出：用户点击的导航项标识。导航项使用稳定标识，例如 `home`、`stores`、`cart`、`profile`，不要依靠易变化的中文标题。

Bar 内部不调用购物车接口，不判断登录，不创建订单。点击事件交给外层容器处理。换新 Bar 时，把相同输入和事件接上即可。

第三方组件不能保证直接复制即可使用：必须适配 ArkUI、当前 SDK、参数和事件。如果提供的是 React/Vue 组件，可以参考视觉重新实现，不能原样放进 ArkTS 工程。

### 4.2 商品卡片等组件使用同样规则

- 商品卡片接收展示数据，发出点击事件，不自己加载商品。
- SKU 选择器接收 SKU 列表，返回选中的 SKU 和数量，不自己下单。
- 状态标签接收订单状态，不自行推断支付结果。
- 页面或 ViewModel 处理请求和状态，组件外观可以随时调整。

此前聊天中的 JSX 风格组件代码仅用于说明概念；实际 `.ets` 应使用 ArkUI 语法。状态装饰器和导航写法应按当前 SDK 选择同一套方案，不混抄不同代示例。

## 6. 分步实施

### 步骤 01：先让空工程跑起来

**目标：** 把环境问题和后续业务问题分开定位。

要做什么：

1. 使用 DevEco Studio 打开当前工程，完成依赖同步。
2. 核对已安装 SDK 与工程配置，选择支持该配置的设备或模拟器。
3. 通过 IDE 配置开发调试签名；个人证书和密码不进入仓库。
4. 保持业务代码简单，先运行 Hello World，尝试修改文字并重新运行。
5. 记录 DevEco、SDK、设备系统版本及运行方法。

**验收：** 能启动、点击和重新安装；退出后可再次打开。若失败，先处理编译、SDK、签名或设备连接，不开始写商城页面。

### 步骤 02：确定页面和基础样式

**目标：** 后续页面具有一致外观。

要做什么：

1. 按第 3 节确认首批页面，画简单线框即可。
2. 集中定义主色、页面背景、正文/辅助文字、错误色，以及间距、圆角、字号。
3. 准备商品占位图和导航图标，记录资源来源及使用许可。
4. 规定加载中、空内容、请求失败、按钮提交中的样式。
5. 为首页快捷区画出两张主功能卡和六个轻量入口；确定主卡文案、图标线条风格、暖色促销色与品牌主色。

**验收：** 两个页面使用相同主题变量；调整主色无需逐页搜索替换。首页快捷区能明显区分主功能卡与轻量入口，不呈现为等宽图标堆叠；占位图不能让用户误认为是真实商品照片。

### 步骤 03：搭四栏主框架

**目标：** 先把入口和页面切换做通。

要做什么：

1. 将 `Index.ets` 作为主容器或从它进入主容器。
2. 创建首页、逛店、购物车、我的四个内容区域。
3. 将底部 Bar 放入独立组件，按第 4 节定义输入和回调。
4. 给详情、登录、地址等二级页面规划统一导航参数。
5. 为搜索保留输入，为列表保留合理的滚动位置；切换底栏不要无条件重置所有状态。
6. 将首页快捷区实现为独立 `QuickEntryGrid` 组件；组件接收入口数据、角标和点击回调，不直接调用接口或写死页面跳转。

**验收：** 四栏可切换；二级页面可返回；Bar 不包含业务请求。首页两张主卡和六个轻量入口可触发正确的占位导航；替换 Bar 或快捷区的颜色、形状后，切换行为相同。

### 步骤 04：连接后端并封装请求

**依赖：** 后端已由负责后端的人启动。

要做什么：

1. 在 `module.json5` 声明 `ohos.permission.INTERNET`。
2. 集中配置 `BASE_URL`。真机使用后端电脑局域网地址；手机的 `localhost` 指手机自身。
3. 先请求 `GET /api/ping`，确认收到 `code: 0` 和 `data: "pong"`。
4. 实现 HttpClient：查询参数编码、JSON 请求、Token 注入、超时、统一响应解析和资源释放。
5. 同时判断 HTTP 状态和响应体 `code`，保留可区分的错误类型。
6. 区分网络异常、响应格式错误、业务拒绝；成功删除接口允许 `data: null`。

| 情况 | 处理约定 |
|---|---|
| 400 | 显示字段或业务提示 |
| 401 | 通知会话层失效；公开浏览不被无限登录跳转打断 |
| 403 | 显示权限不足，不循环重试 |
| 404 | 页面资源不存在或列表空状态，按场景处理 |
| 409 | 提示库存或状态冲突，刷新相关数据 |
| 500、断网、超时 | 显示可重试状态；写操作不盲目重发 |

连接失败依次检查：电脑端接口是否可访问 → 后端监听地址 → 同一局域网及网络隔离 → 防火墙端口 → App 权限和设备网络策略。开发期 HTTP 限制按当前 SDK 文档处理，正式环境使用可信 HTTPS；不要用关闭证书校验解决问题。

**验收：** 真机能收到 pong；断网能看到明确错误；恢复网络后可重试；日志不包含密码、完整 Token 或地址信息。

### 步骤 05：定义数据模型和数据来源

**目标：** 页面既能先开发，也能稳定切到真实后端。

要做什么：

1. 先定义用户、店铺、商品摘要、SKU、购物车项和通用响应类型。
2. 请求类型与响应类型分别定义；不要把一个万能对象用于所有接口。
3. 建立 API 类及 Repository，页面只访问 Repository 或 ViewModel。
4. Mock 数据遵循实际合同，覆盖成功、空列表、售罄、过期登录等场景。
5. Mock 由明确的开发配置控制。真实接口失败时显示失败，不自动切假数据。
6. 后续接口变化通过转换层适配；金额不由客户端决定，ID 的类型按实际合同处理。

**验收：** 同一商品列表可切换 Mock 和真实数据；页面组件不用跟着改；当前缺失图片字段不会引发空值崩溃。

### 步骤 06：登录、注册与会话

接口：`POST /api/auth/register`、`POST /api/auth/login`、`GET /api/auth/me`。

要做什么：

1. 完成账号密码表单、校验、提交中状态和错误展示。
2. 注册成功后执行登录或明确引导登录；注册接口不返回 Token。
3. 保存 Token，启动时通过 `/me` 校验。开发期存储方案与正式版加密方案分别安排。
4. 游客可浏览首页、店铺、商品；购物车等受保护操作再引导登录。
5. 登录成功回到来源页面，要求用户重新确认结算等写操作。
6. 多个请求同时返回 401 时只触发一次登录跳转；清理用户私有缓存。
7. 本地退出清除 Token 和用户数据。当前没有服务端撤销 Token 接口。
8. 当前是消费者 App，商家账户登录后说明角色不支持，避免进入消费者交易流程。

注意：`/me` 断网不等于 Token 无效，不能把所有网络错误都当作退出登录。没有 Refresh Token，不实现自动刷新假流程。

**验收：** 正确/错误密码、注册后登录、重启恢复、401、断网校验、退出后换账号均正常；账号 A 的购物车不残留在账号 B 页面。

### 步骤 07：店铺、搜索与首页

接口：`GET /api/public/stores`、`GET /api/public/stores/products/search`、`GET /api/public/stores/{storeId}/products`。

要做什么：

1. 先做店铺列表，再做店铺商品，最后做跨店搜索。
2. 搜索支持关键词和店铺筛选；筛选变化后从第一页开始。
3. 防止较早的搜索响应覆盖较新的搜索结果，可用请求序号校验。
4. 请求分页从 1 开始。当前返回数组，无 total/hasMore；与后端确认 size 上限，并用固定页大小实现“加载更多”。
5. 首页按第 3.1 节组合快捷区、店铺和普通商品数据；促销主卡在步骤 14 接入真实活动数据前，可以展示明确标注的演示状态，普通列表不要宣称个性化推荐。
6. 真实接口可用后，精选店铺跳转店铺列表或精选店铺页，热门商品跳转搜索/商品流；入口组件的视觉层不关心数据来自 Mock 还是真实接口。

分页临时规则：不足一页可判断结束，恰好一页则允许再请求一页，空页后结束。这个规则依赖后端实际页大小，最终建议升级分页合同。

**验收：** 无商品、中文搜索、快速改关键词、换店铺、加载更多和返回列表都正确；快捷区的每个已开放入口都有明确去向，页码不会连续跳过。

### 步骤 08：商品详情与 SKU

接口：商品详情、`GET /api/public/skus/{skuId}/availability`、`POST /api/cart/items`。

要做什么：

1. 页面参数携带 `storeId`、`spuId`；SKU 操作使用 `skuId`。
2. 展示商品描述与 SKU 列表。当前是 skuName，不假设存在颜色×尺寸规格矩阵。
3. 选择 SKU 后展示对应价格、库存，数量不得小于 1。
4. 没有可购 SKU 时显示不可购买；提交期间禁用按钮。
5. 可刷新 availability，但最终可购买与库存以后端写接口为准。
6. 成功后刷新购物车状态；失败保留用户选择并展示提示。

**验收：** 单 SKU、多 SKU、零库存、商品下架、连续点击、未登录加购和后端 409 均可处理。

### 步骤 09：购物车

接口：`/api/cart/items` 的 GET / POST；`/api/cart/items/{id}` 的 PUT / DELETE。

要做什么：

1. 按店铺分组展示，购物车项 ID 与 SKU ID 分开保存。
2. 实现单选、全选、数量修改和删除。失效商品禁止参与结算，允许删除。
3. 初版数量更新可在请求期间禁用该项按钮，避免乱序响应。
4. 请求成功后刷新权威数据；失败恢复数量或重新加载。
5. 统一角标口径，例如所有可购项的数量总和；勾选状态保留在客户端并按返回项校正。
6. 底部显示勾选数量与预估金额；客户端展示金额使用统一精度处理，成交金额以后端为准。

**验收：** 数量、角标、全选状态一致；删除最后一项显示空态；库存变化不让失效项结算；跨店商品能一起勾选。

### 步骤 10：地址管理

接口：`/api/addresses` 的 GET / POST；`/api/addresses/{id}` 的 PUT / DELETE。

要做什么：

1. 完成列表、新增、编辑、删除、默认地址和结算选择模式。
2. 字段遵循文档长度要求；PUT 完整提交所有必填字段。
3. 当前没有省市区数据接口，第一版可用文本输入；使用地区选择器前确认独立数据来源。
4. 默认地址状态以后端保存后的列表为准。
5. 地址删除后清理结算页已选 ID，进入结算时重新确认有效性。

**验收：** 无地址能引导新增；保存后可返回选择；完整编辑不丢字段；已删除地址不会继续提交。

### 步骤 11：确认订单与原子结算

接口：`POST /api/checkouts`、`GET /api/checkouts/{checkoutGroupId}`。

要做什么：

1. 从购物车传入选中的 cartItemIds，重新获取购物车和地址数据。
2. 显示店铺分组和地址；当前没有独立报价接口，提交前金额标为预估，成功后展示后端总额。
3. 在发起一笔结算前生成幂等 Key，绑定当前用户及固定请求内容。
4. 提交期间禁用按钮；同一次请求超时重试，必须复用 Key 和原请求内容。
5. 保存未确认结算的 Key 和必要恢复数据；提交状态不能只放在按钮局部变量中。
6. 成功后记录 checkoutGroupId，刷新购物车，进入结算结果页。
7. 结果页从后端查询结算组及子订单；不把“订单已提交”写成“支付成功”。

**超时恢复规则：** 超时可能意味着后端已经创建订单。状态不明时展示“正在确认订单结果”，按幂等合同重试原请求；不要生成新 Key。已有 groupId 时直接查询。没有 groupId 且无法重放时，保留未确认状态并引导查询订单，需要后端补充按幂等 Key 查询能力时记录需求。只有用户明确发起新的结算意图，且上一笔已澄清，才生成新 Key。

当前不使用 prepare 和分步创建子订单接口编排普通结算。真实支付未接入时结果页显示待付款与真实可用操作；模拟支付只允许受控开发验收环境使用，默认关闭，不能进入用户发布包。

**验收：** 两个店铺一次结算产生对应子订单；连点不会创建两组；超时重试复用原 Key；401、地址失效、409 可恢复；退出再进入能查询已创建订单。

### 步骤 12：订单列表与详情

接口：`GET /api/orders`、`GET /api/orders/{id}`、`POST /api/orders/{id}/cancel`，以及结算组取消接口。

要做什么：

1. 列表按真实状态展示；当前不分页，少量开发数据可本地过滤，不能伪造服务端分页。
2. 详情使用订单内的收货地址快照，不用当前默认地址替代历史地址。
3. 商品项目前可能仅有 SKU 名称快照，店名、商品名、图片等缺失字段应记录给后端；不要依赖当前商品一直存在。
4. 取消前确认，区分取消一个子订单和整个结算组的按钮含义。
5. 取消完成或遇到 409 后刷新订单和结算组状态。
6. 倒计时只辅助展示，付款/关闭状态以后端为准。订单接口没有 serverTime 时，记录后端补充需求。

**验收：** 重进详情状态最新；已取消订单不能重复操作；地址修改不改变历史订单；所有按钮与当前后端状态对应。

### 步骤 13：售后

接口：eligible-orders、`POST /api/after-sales`、售后列表与详情。

要做什么：

1. 使用后端返回的可售后项确定入口，必要时结合订单详情补足可读商品信息。
2. 选择数量并填写原因；审核金额和最终可申请数量以后端为准。
3. 提交后展示申请编号和状态，支持查看商家说明。
4. 页面文案区分“审核通过”和“退款到账”。

**验收：** 不可申请的项不能正常提交；非法数量有反馈；提交中不可连点；重复请求被拒绝时可查看已有记录。当前接口没有通用幂等承诺，超时后先查记录，不自动重复提交。

开发验收需要已付款订单，可由后端提供测试数据或在隔离开发环境完成模拟支付准备。

### 步骤 14：限量促销与抢购

接口：公开促销列表/详情、提交 reservations、查询抢购结果。

要做什么：

1. 首页添加真实活动入口，详情根据 serverTime 计算时间偏移；与后端确认无时区时间字符串的时区约定。
2. 使用独立 requestKey 标识同一次抢购意图，重试复用。
3. 先检查外层 ApiResponse.code，再处理 data.code；拿到资格不等于订单已经创建。
4. 展示处理中，按 1 秒、2 秒、3 秒等退避节奏查询，给定总超时。
5. 页面离开、退出登录、应用转后台时停止无意义轮询；回到前台按需查询当前状态。
6. 有 orderId 后进入订单详情；超时显示仍可查询的状态，不提示“必定抢购失败”。

**验收：** 未开始、已结束、售罄、限购、资格重复、异步延迟和离页停止轮询均覆盖；倒计时归零后仍以后端结果为准。

### 步骤 15：换好看的组件与完善体验

**前提：** 主交易流程已通过，不在同一次改动中同时换结算逻辑和整套视觉。

要做什么：

1. 依次优化底部 Bar、商品卡片、SKU 弹层、订单卡片。
2. 每换一个组件，保持输入、事件、稳定 ID 和数据来源合同。
3. 检查底部安全区域、软键盘遮挡、字体放大、小屏布局和点击区域。
4. 加入适度动效，观察列表滚动和切页性能。
5. 页面返回时避免闪空白，失效数据允许刷新，按钮提供加载反馈。

**验收：** 换 Bar 后导航及角标正常；换 SKU 弹层后仍提交正确 skuId；弱网不多次提交；没有内容被系统栏或键盘遮住。

### 步骤 16：真机回归与阶段交付

按下一节清单完成回归，记录设备、后端版本、结果、已知限制。保留一段完整操作录像或关键截图，便于以后换组件后比较。

**演示版完成标准：** 可安装运行，真实接口主流程可走通，失败可恢复，缺失的支付与履约能力有明确说明。

**正式版完成标准另行评估：** 图片与支付、退款、履约等后端合同补齐；环境、签名、存储、隐私说明和当前应用分发要求准备完成。演示版通过不代表已满足上架或正式交易条件。

## 11. 新对话接手与教学推进规则

### 11.1 使用目的与材料边界

用户会将本指南交给新的对话，希望助手结合实际代码、Git 提交和验收结果，判断下一小步并带着用户完成。默认采用逐步教学模式：解释、实施或指导、验证、记录，然后推进。用户明确要求直接实现时再调整节奏。

本指南提供路线和接手规则，不代表任何步骤已经完成。第 2 节是 2026-09-09 的起点快照，不是未来每次接手时的实时状态；第 5 节复选框也需要证据支持。

新对话不会自动继承旧对话的记忆，文档中的本地路径也不保证在新环境可读。接手时先检查以下材料是否可用：

- 本指南，以及项目已有的 AGENTS.md 等约定。
- 当前鸿蒙工程源码，包括尚未提交的修改。
- Git 分支、HEAD、近期提交及相关文件差异。
- 配套接口文档；需要核对接口时再读对应后端代码。
- `docs/开发进度与交接.md`（如已建立），以及构建、真机或接口验证记录。

如果只能看到本指南，就只能给出暂定学习安排，不能声称已经检查代码或提交。说明缺少哪项材料，并请用户提供对应目录、文件或命令输出；不必要求整个后端或全部历史才能开始。

### 11.2 每次接手先做只读核对

1. 确认当前工作目录和工程类型，读取项目约定。
2. 若目录是 Git 仓库，查看 `git status --short`、`git branch --show-current`、`git log -n 12 --oneline --decorate`。
3. 查看 `git diff --stat` 与 `git diff --cached --stat`，再读取与当前步骤有关的实际 diff、新文件和源码。未跟踪文件需要单独读取，不能只看 diff。
4. 对关键提交使用 `git show --stat <提交号>` 和必要的文件差异，确认提交实际做了什么。近期记录不足时，按有关文件查更早历史，不盲目读取全部提交。
5. 对照交接记录和本指南的验收条件，检查代码是否仍然存在、是否被后续提交改变，以及验证证据是否对应当前版本。
6. 没有 Git 仓库时，按源码和用户提供的记录继续判断，并标注无法核验提交历史。不要自动初始化仓库、切分支、丢弃修改、提交或推送。

提交标题只是检索线索。例如“完成购物车”不能证明数量更新、角标、失效商品和跨店勾选均已验收；已有代码也可能尚未编译通过。反过来，未提交的工作同样属于真实进度，应保留并纳入判断。

### 11.3 进度判定和下一步选择

为有关步骤使用以下状态：

| 状态 | 判断依据 | 后续处理 |
|---|---|---|
| 未开始 | 未发现相关实现 | 从该步骤最小任务开始 |
| 进行中 | 只有部分实现或仍存在已知问题 | 补当前缺口，不重做已有部分 |
| 待验收 | 实现基本齐全，但缺构建、真机或业务验证证据 | 优先验证，不直接宣告完成 |
| 已完成 | 实现与对应验收证据一致，未发现后续改动使其失效 | 跳过已完成部分 |
| 阻塞 | 明确缺少设备、后端能力或必要信息 | 记录解除条件，推进不依赖该条件的小任务 |

选择下一步时，优先补阻碍当前目标的前置缺口，再完成当前步骤的验收，之后进入下一依赖步骤。已被有效验证且相关代码没有变化的内容无需反复验收。

文档、提交记录与当前代码不一致时，列出具体差异，以当前实现说明“已有何物”，以有效验收说明“哪些行为已验证”，再修正进度。用户说“做完了”可作为线索，但未提供测试证据时注明“用户反馈通过”或“待独立验证”。

首次接手输出一个简短结论即可：

```text
已核对：工程位置、分支/HEAD、相关提交、未提交修改、进度记录。
目前位置：步骤 XX，状态为进行中/待验收等。
依据：具体文件、提交差异或验证记录。
本次下一小步：一个明确任务。
完成标准：用户能执行的操作和可观察的结果。
尚缺信息：仅列真正影响本次工作的项目。
```

### 11.4 默认如何“带着我做”

每轮选一个可独立验证的小任务，不一次发出整个模块的大量代码。例如步骤 09 可以分为“读取购物车”“分店展示”“数量更新”“勾选结算”几轮。

每轮按以下顺序组织：

1. **说明目的：** 这一小步解决什么问题，与已完成内容如何连接。
2. **指出位置：** 操作哪个文件，先看哪段代码；新文件说明职责。
3. **给出操作：** 提供必要代码或清晰修改步骤，解释关键状态和事件，不堆无关概念。
4. **执行验证：** 写明在 IDE、设备或接口工具中做什么，以及预期看到什么。助手实际能执行的检查可以执行，但应区分自动验证与待用户真机确认。
5. **记录结果：** 收到结果后再标记完成；失败先围绕本次修改定位原因，不立即跳到下一模块。

默认用户自己操作和理解，助手给出指导；用户要求代写或直接修改时，完成当前约定小任务并讲解。提供代码不等于用户已经运行成功，不能在等用户操作时把当前步骤写成已完成。

用户中途提问时先解释，再回到当前小任务；不要因为问了一个概念就丢失正在推进的步骤。若用户明确调整目标或顺序，记录变化及前置依赖影响。

### 11.5 跨对话进度记录

本次仅完善指南，并未执行商城开发，所以不预先创建“已完成”的业务记录。后续记录采用如下格式：
